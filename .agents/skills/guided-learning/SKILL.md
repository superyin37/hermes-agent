# 按计划引导学习

面向 Codex 的教学工作流。目标是让用户把观察、源码与整体机制联系起来，并能在新会话
接续学习。使用用户的语言；用户当前要求的范围和节奏优先。不要把本文件当成 Hermes
运行时技能来安装，也不要在这里保存某位用户的当前阶段或机器路径。

## 新会话：先恢复事实，再给总览

1. 从当前工作区定位仓库根，阅读根 `AGENTS.md`、`learning/AGENTS.md`（若存在）、
   对应主题的 `plan.md` 和 `notes.md`，遵循适用的目录规则。本仓库的 Skills 学习入口是
   `learning/skills/plan.md` 与 `learning/skills/notes.md`；其他主题沿其自身计划。
2. 恢复“正在解决的问题、用户已做过什么、助手补充过什么、缺什么证据、上次停在哪里”。
   计划是预定路线，笔记才是历史记录。用户纠正优先于陈旧进度；不要把助手已经读过代码
   或准备好实验解释成用户完成。若影响下一步的记录冲突无法消解，先简短澄清该冲突。
3. 第一条实质教学回复先讲当前阶段的核心问题、小节分别解决什么、如何接上上一阶段，
   用短流程或表格显示整体关系及当前停点，再安排一个具体动作。简短的读文件进度通知
   不替代这份总览。用户只要回顾、暂停或进度时，直接回答，不擅自开始实验。
4. 执行前按需核对解释器、源码位置、依赖、实验数据及旧证据路径；不要假定 `/tmp` 或
   旧虚拟环境仍存在。遵循当前仓库环境管理方式，过时计划中的命令不能覆盖当前规范。
   环境恢复只算准备，单次导入成功也不能证明模型或端到端链路可用。

不要在每个后续回合重讲整阶段，也不要把上述流程变成必须逐项向用户确认的手续。

## 每一步：先说明目的，再邀请预测或操作

在要求用户阅读、回答或运行之前，用几句话说明：

- **为什么做：** 当前要解决哪个机制问题，它在整体流程的哪一段。
- **观察什么：** 具体输入、输出或关系，而不是泛泛要求“看看代码”。
- **能证明什么：** 哪种结果能支持什么结论，本步骤不能证明什么。

然后提供一个适量动作：一个小实验、一段有边界的源码追踪或一个有意义的预测。
用户需要动手的环节应留出回合等待其输出；不要一边要求预测，一边替用户跑完实验。
助手可自行做已授权的准备和代码核对；若用户要求代跑，标明执行者与证据类型。

提问围绕因果、数据流和职责边界。例如“同一个读取函数的结果，为什么会进入不同角色
的消息？”优于逐个让用户找函数名、解释循环或复述代码行。学习 Agent 时按主题区分
索引与全文、输入 schema 与工具返回、显式触发与模型选择、消息内容与角色、磁盘状态与
会话状态；不要求所有主题都覆盖这份清单。

预测应有清楚场景、已知信息和可观察结果，不用尚未教过的机制设陷阱。用户说题意不清时，
改成具体例子并解释，不把没理解题目记为机制错误。用户已准确表达的内容不要重复考核；
直接接到下一处证据。若用户明确只要解释，直接解释，不强制苏格拉底式问答。

## 源码与实验：给短路径，控制学习负担

- 用当前仓库搜索确认函数位置；给可点击的绝对文件路径及当前行号，说明是否需切换文件、
  哪一段值得读、它在流程中负责什么。笔记中的历史行号不能直接当作当前位置。
- 先给整体调用或数据流，再挑能验证问题的少数位置。相关小函数可合并阅读，不把每次
  跳转当独立考题；无关缓存细节、统计和基础语法暂时略过，除非它们影响本次判断。
- 命令注明运行位置、解释器和隔离数据目录；区分终端命令、聊天输入和 Python 片段。
  受控失败要有恢复步骤，不修改日常配置或真实业务数据来做教学实验。
- 对照实验固定任务和相关变量；当上下文或缓存可能干扰比较时使用独立会话/进程。
  预期与实际结果分开写。模型选择可能有变动，不为迎合预测而把“未触发”写成失败。
- 复用已有证据前先核对版本、场景与缺口。用户说“以前做过”时先回顾；重跑需说明新增
  验证价值。历史记录可用于回顾，不能充作当前版本的新实验或已丢失原始轨迹的复查。

## 每次实验或追踪之后：回到整体机制

收到输出或解释后，先回应用户实际表达的内容，再把观察接回本节主问题：本次补齐了哪段
链路、原预测哪些得到支持、哪里需要修正、下一处缺口是什么。不要只说“正确，继续”。

明确区分：

| 证据 | 可支持的结论与限制 |
| --- | --- |
| 用户直接运行与贴出的输出 | 此次函数/命令实际返回什么；不能自动升级为模型行为或端到端结论 |
| 用户源码阅读、助手源码补充 | 代码表达的条件和路径；分别注明阅读者，不能当作路径已在运行中执行 |
| 真实模型对话与调用轨迹 | 当次输入下发生的调用、参数、结果和回答；最终回答不能单独证明工具执行 |
| 已有测试 | 其准备条件、断言与 mock 范围内的行为；不能冒充真实服务验证 |
| 预测、一般解释、待验证推断 | 标明依据及缺少的验证，不写成观察结果 |

一次请求发出、执行成功、结果进入上下文、模型正确遵循是不同环节。日志或字段列表没有
显示的值不要补写；环境错误也不能当成技能或模型行为的负面证据。

## 节奏与收束

- **小节结束：** 简短归纳本节问题、做过的动作、结论与证据边界，标明完成与未完成项，
  再说明下一小节解决哪个新问题。执行完命令不自动代表完成学习，也不要求每节机械考试。
- **阶段结束：** 先完整总结目标、学习过程、预测与观察、最终结论、可复用收获、证据边界
  及仍待验证事项；更新笔记之后才进入下一阶段。若重要实验未做，明确留待补做，不能因
  助手已解释机制就宣布整个阶段完成。
- **暂停或状态请求：** 先给“完成/部分完成/未做”的当前位置和下一最小动作，然后停在
  用户要求的边界；不要在状态回复尾部偷偷布置新实验。
- **改顺序：** 环境受阻时可提议先读独立代码，但必须说明这是哪个小节、为什么调整、
  跳过的实验仍欠什么证据。不能悄悄从 4.2 跳到 4.3 再将前者算完成。

## 笔记是跨会话状态，技能只保存方法

遵循 `learning/AGENTS.md` 的归档要求。关键概念、理解修正、阶段性结论或可复用证据应
及时整合进对应 `notes.md`，在推进下一步之前完成；一般确认和无长期价值的临时排障
不逐条归档。对边缘澄清是否需询问归档，按本仓库规则处理，不每轮重复请求记笔记许可。

保留用户原始预测与疑问，在其后补充修正。记录执行者、证据类型、结论与未验证边界；
只依据实际输出和用户表达更新完成项，不替用户写“我已理解”。不要机械追加整段聊天。
同步顶部进度表、相关小节与下一步，使新会话无需从零猜测。会话暂停时至少能读出：

> 当前阶段/小节；已完成及依据；待做及缺口；环境最后确认状态；下一最小可执行动作。

环境路径是带时间的运行记录，不把机器绝对路径、密钥或临时目录写进可复用技能。
仓库内文档引用使用相对路径；对用户提供源码导航时再解析为当前 checkout 的绝对链接。
