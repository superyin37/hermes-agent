### 2.2 容量边界预测（2026-10-13）

**用户原始预测：** 目标上限 20 字符，已有两条各 8 字符的 entry，加 3 字符分隔符共 19。对新增 1 字符条目与将原条目从 8 字符替换成 9 字符两个场景，用户回答“预计2能成功，1会超限制”。

**助手核对：** add 的新总量为 8+3+8+3+1=23，replace 为 9+3+8=20。代码以分隔符连接后的字符数比较，只有大于上限才拒绝；这是整个 target 的字符预算，不是单条长度或模型 token 数。原预测与下述用户实际输出一致。

**用户运行证据：** 实验 home 为 `/home/yin-hanyang/.local/share/hermes-learning/memory.YgSYyO/capacity.cmx0td5q`，实际调用 `memory_tool`，store 的 memory 上限为 20。初始文件为 `AAAAAAAA\n§\nBBBBBBBB`；新增 C 返回 `success=false`、`usage=19/20`、原 current_entries，且 `path.read_bytes() == before` 为 True。随后把 A 条目改为 9 个 A，返回 `success=true`、`done=true`、`usage=100% — 20/20 chars`、`entry_count=2`、`replaced_entry=AAAAAAAA`；磁盘为 `AAAAAAAAA\n§\nBBBBBBBB`，长度 20。

**本次结论与边界：** 真实文件 I/O 支持新增超限拒绝并保留原文件、替换恰好达到上限可提交；没有观察到自动删除其他条目腾空间。结果中的整理提示是建议后续操作，不是工具已自行整理。独立容量 home 不替代主实验 home-a；20 字符是本次手动构造 store 的限制。不能将 add 失败证据自动推广到 replace 失败。

**用户超限替换运行证据：** 将 9 个 A 改为 10 个 A 后，工具返回 `success=false`，报错预计占用 21/20，实际 `usage=20/20`、current_entries 仍为原两条；文件字节比较为 True，store 条目和磁盘也均保持 `AAAAAAAAA`、`BBBBBBBB`。用户解释：“看起来会保留原内容呢。”

**容量小结：** 原预测成立；三项边界（新增超限、替换恰好满额、替换超限）均有真实工具函数与文件输出。替换失败时对象条目也未变，补足了此前 add 失败不能代替的分支。结论限于本次容量拒绝路径，不扩张为所有故障、并发或批次都已验证。

### 2.2 批次提交预测（2026-10-13）

**用户原始预测：** 同一次 operations 中先将 C 替换为 D，再删除不存在的 ZZZ；用户回答：“我预计时原来的 `C / BBBBBBBB`，因为我预计批量操作会在整批通过后才提交”。

**用户失败批次运行证据：** 调用真实 memory_tool 后返回 `success=false`，错误明确为 `Operation 2 (remove): no entry matched 'ZZZ'. No operations were applied (batch is all-or-nothing).`，usage 为 12/20；文件字节比较为 True，对象条目为 C／BBBBBBBB，磁盘为 `C\n§\nBBBBBBBB`。第一项替换出的 D 未保留，原预测得到支持。

**助手源码解释：** `_batch` 在 `working = list(entries)` 副本上逐项尝试；第二项报错就返回错误字典。外层 `_mutate` 收到字典直接返回，不执行后面的更新条目与写文件。因此该路径并不是第一项先写盘、失败后再写回旧值。阅读入口为 `memory_tool_store.py` 421～432 与 265～272 行；这部分当前记为助手核对，不声称用户已经解释。

**证据边界与下一步：** 本次验证第二项无法定位时的整批拒绝，不证明进程崩溃、并发或所有 I/O 故障下的行为。下一步以同一 12/20 状态预测“先新增 8 个 D，再删除 8 个 B”：中间候选为 23 字符，最终为 12，判断是否允许。当时成功批次与最终容量规则仍待验证；后续结果见下文。

**用户最终容量预测与源码解释：** 用户回答“按最终总量成功提交”，理由为“超限检查仅在全部操作完成后才统一进行一次而不是每一次操作都进行”，并引用 `new_total = len(ENTRY_DELIMITER.join(working))` 与 `if new_total > limit`。这与 `_batch` 循环后的最终容量检查一致；预测不是新的运行证据。

**用户成功批次运行证据：** 同一批次先 add DDDDDDDD、再 remove BBBBBBBB，返回 `success=true`、`done=true`、`Applied 2 operation(s).`、usage 12/20、两条 entry，`removed_entries={"2":"BBBBBBBB"}`。对象条目为 C／DDDDDDDD，磁盘为 `C\n§\nDDDDDDDD`，最终字符数 12。与用户关于最终容量的解释一致，中间工作副本超限不代表磁盘写入过超限内容。

**2.2 小结：** 通过用户预测、源码解释及实际工具／文件输出，已验证定位歧义拒绝、唯一定位整条替换、容量超限拒绝且文件不变、满额允许，以及批次失败不保留前项修改、合法批次按最终容量提交。原 VEGA 实验依用户要求跳过，不改写为执行过；后续唯一定位实验提供了另一份整条替换证据。精确匹配优先有源码解释，未专门运行该分支。

### 2.3 两个旧 store 的顺序追加：预测
